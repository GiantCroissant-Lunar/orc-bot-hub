# S8 — fantasim bundles, service tiers, and package use

- Date: 2026-08-16
- Scope: `fantasim-app-godot` snapshots from 2026-06-25 through 2026-08-03, with the local Archi/Foundation sources used only to verify the intended package semantics.
- Decision frame: RFC-0001's `contracts/`, `libs/`, `plugins/`, and `hosts/` split; ADR-0002 candidate authority; ADR-0004/0009 derived-state isolation; and ADR-0005 versioned artifacts.

## Result

The reported design is real, but it is historical rather than the current Fantasim architecture.  The complete PCK + collectible-ALC + ServiceArchi-four-tier system is in the 2026-06-25 snapshot; the 2026-08-03 snapshot instead calls a content-addressed *runtime world data package* a bundle, and uses PluginArchi/RegistryArchi only for in-process composition.  The snapshot sweep found no PCK/ALC host implementation in the intervening 2026-07-18 snapshot, so this is useful scar tissue and a few good seams—not a working template for making Orc Bot's one-scene Godot validation host dynamically modular.

The three transferable ideas are: keep a narrow Orc-owned plugin contract over PluginArchi; use RegistryArchi only for runtime capability/provider selection and owner-scoped removal; and make shared cross-context contracts plus an unload proof an explicit acceptance test.  Do not import Fantasim's PCK hot reload, its four-tier service graph, or its ambient `IServiceProvider` pattern into the RFC-0001 bootstrap.

## 1. Bundles: what they actually were

1. **A historical application bundle was a PCK container, optionally carrying a managed plugin assembly; it was not one or the other.** A UI bundle such as `panel-world-viewer` declared an entry scene, while `plugin-world-globe` declared `Plugin.WorldGlobe.dll`; the loader mounted the PCK, instantiated the entry scene if present, then extracted and registered the managed assembly if present.  The manifest model also had `residentScripts`, deliberately binding a host-resident Godot C# type to a freshly instantiated PCK scene. (prior-attempt (2026-06-25) fantasim-app-godot/project/bundles/panel-world-viewer/manifest.json:1; prior-attempt (2026-06-25) fantasim-app-godot/project/bundles/plugin-world-globe/manifest.json:1; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleHost.cs:65-121; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleManifest.cs:9-92)

2. **The on-disk convention was source directory `project/bundles/<bundle-id>/`, emitted as `<bundle-id>.pck`.** `content-app` existed only to run `--export-pack`; its `bundles/` directory was a junction to the source bundle tree so the main `complete-app` export excluded it.  The outputs were versioned under `build/_artifacts/<version>/godot/win-x64/bundles/`, which is the compatible part of the design: one build version owns every emitted bundle. (prior-attempt (2026-06-25) fantasim-app-godot/Taskfile.yml:13-35; prior-attempt (2026-06-25) fantasim-app-godot/project/hosts/content-app/export_presets.cfg:1-16)

3. **A bundle build was a named Task target plus a per-bundle Godot export preset, not an assembly-packaging system.** For example, `build:bundle:plugin-fantasim` first copied the plugin DLL and several private DLLs into the bundle directory, then executed `Godot --headless --path content-app --export-pack "plugin-fantasim PCK" .../plugin-fantasim.pck`; the matching preset includes only `bundles/plugin-fantasim/*`.  This makes the PCK the distribution envelope for scenes/assets *and* staged DLLs, while the exported executable remains a separate UnifyBuild artifact. (prior-attempt (2026-06-25) fantasim-app-godot/Taskfile.yml:335-352; prior-attempt (2026-06-25) fantasim-app-godot/project/hosts/content-app/export_presets.cfg:291-315)

4. **The runtime load path was concrete and two-part.** The actual code was:

   ```csharp
   if (!_vfs.LoadPck(pckPath)) return;
   // ... instantiate manifest.EntryScene when supplied ...
   var tempPath = _extractor.ExtractAllToTemp(bundleResPath, pluginAssembly);
   await _pluginHost.AddGroupAsync(bundleId, manifest?.DisplayName ?? bundleId, tempDir);
   ```

   `LoadPck` is a direct `ProjectSettings.LoadResourcePack(pckPath)` call; `ExtractAllToTemp` extracts every `.dll` it finds in the PCK beside the declared plugin DLL, so PluginArchi can resolve plugin-private dependencies from that directory. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleHost.cs:65-121; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleVfs.cs:7-10; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/DllExtractor.cs:36-85)

5. **“Unload” only unloaded the managed group and instantiated scene; it could not unmount the PCK.** The actual teardown is `RemoveGroupAsync(bundleId)`, `_sceneHost.RemoveScene(bundleId, ...)`, and removal from the in-memory map.  `BundleVfs.UnloadPck` is an empty method whose comment says Godot does not support individual PCK unload and the VFS entries persist until restart.  This exactly corroborates RFC-0001's warning that repeated PCK reloads monotonically grow the mounted VFS. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleHost.cs:146-168; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleVfs.cs:12-18; docs/rfc/0001-bootstrap-slice.md:262-267)

6. **The manifest was an entry-point/payload description, not a sound dependency declaration.** The old fields are `bundleId`, `displayName`, `version`, `entryScene`, `pluginAssembly`, and `residentScripts`; a later `content.pcks` / `managed.assemblies` shape existed, but `BundleHost.LoadAsync` still only uses the first `PluginAssembly` to decide what to extract/load.  Runtime profiles can list bundle IDs in ordered phases, and auto-load heuristically puts filename prefix `plugin-` before all other PCKs, but there is no manifest `dependsOn`, no dependency closure, and no topological load validation. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleManifest.cs:9-92; prior-attempt (2026-06-25) fantasim-app-godot/project/contracts/App.Bundles.Contracts/RuntimePhase.cs:6-25; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleRuntimeService.cs:47-62, 223-243)

7. **In the newest snapshot, “bundle” means immutable world data, not a code/content PCK.** `Fantasim.Runtime.World` opens an `IRuntimeBundle` through three read methods; its documented layout is `manifest.rwp` plus `payloads/sha256/<prefix>/<hash>.bin`.  It expressly carries no producer state and is read through a directory or a Godot-VFS delegate, not mounted, unloaded, or loaded into an ALC.  This is closer to an immutable candidate artifact than to a plugin package. (prior-attempt (2026-08-03) fantasim-app-godot/project/runtime/README.md:11-31, 131-170)

## 2. The four tiers, exactly

The 2026-06-25 canonical document names the layers and service roles precisely:

| Tier | Exact role and marker | Required location/lifetime | Allowed project references |
| --- | --- | --- | --- |
| **1** | Service **interface**, `[ServiceContract]` | Resident `*.Contracts`, shared with the parent ALC; never unloads | T1 only |
| **2** | Service **proxy**, `[RealizeService(typeof(IFoo))]` | Resident; generated forwarding selector; never unloads | T1 only |
| **3** | **Real service**, `[ServiceImplementation]` / `[AutoRegister]` | Plain C# in a collectible ALC; unloadable | T1 and T3, expressly not T2 |
| **4** | **Provider**, `[ServiceProvider]` | Collectible ALC; owns/constructs T3 or external resources; unloadable | T3 and T4, not T1 |

The historical Fantasim layer mapping is evidenced in its canonical design; the reference allowances are enforced by the ServiceArchi analyzer, rather than being a convention. (prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:10-27, 122-142; scarlet-projects/service-archi/vault/Architecture/Tiers.md:7-34; scarlet-projects/service-archi/dotnet/ServiceArchi.Analyzers/TierReferenceAnalyzer.cs:111-120)

8. **Tier membership was determined by project metadata and role attributes, not by the PCK name.** The active old proxy project sets `ServiceArchiTier` to `T2`, references only its T1 contract, and uses `[RealizeService(typeof(IConfigService))]`; the contract supplies `[ServiceContract]` and a selection policy.  The analyzer treats a project that contains a proxy as T2 even when the property is absent. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Config.Proxy/App.Config.Proxy.csproj:5-25; prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Config.Proxy/ConfigServiceProxy.cs:7-23; prior-attempt (2026-06-25) fantasim-app-godot/project/contracts/App.Config.Contracts/IConfigService.cs:1-21; scarlet-projects/service-archi/dotnet/ServiceArchi.Analyzers/TierReferenceAnalyzer.cs:183-199)

9. **The swap mechanism was deliberately per-call lookup, not cached references.** The generated proxy emits `ResolveService()` and every generated member forwards through it; hence unregistering an old T3 implementation and registering a replacement can change the next call without rebuilding resident callers.  The canonical document also distinguishes this four-role meaning of “Tier” from unrelated `Bootstrap.cs` comments labelled Tier 1–5; conflating them was identified as a source of bad reasoning. (scarlet-projects/service-archi/dotnet/ServiceArchi.SourceGen/ServiceProxyGenerator.cs:205-250; prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:132-159)

10. **The intended live boundary was “ALC service publishes a message; resident Godot node applies it.”** That avoids a collectible plugin holding a `Node`, which would pin the ALC through Godot's native scene tree.  The historical `WorldGlobeBackendPlugin` demonstrates the model by publishing `ApplyPlateColorsCommand` onto `IMessageBus`, while the canonical design explicitly puts Godot-derived `Node`, `Control`, `Resource`, `RefCounted`, and `GodotObject` types in the resident layer. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/Plugin.WorldGlobe/WorldGlobeBackendPlugin.cs:15-28, 232-245; prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:18-27, 87-119)

The newest snapshot directly references PluginArchi 0.1.5 and uses `PluginRegistry`, `PipelineExecutor`, and `IPlugin` in `WorldComposer`; its Godot smoke host manually registers concrete plugins. ## 4. Breakage and scar tissue worth retaining

11. **PCK reload was never a true resource unload.** Rebuilding a PCK could replace scene resources, but VFS mounts remain; bundle-specific scene freeing does not change that.  This is a process-lifetime leak model, not a safe general reload loop. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleVfs.cs:12-18; prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:70-80)

12. **The first ALC reload design overwrote the same extracted DLL while the old context still held its file handle.** The repair was a session-unique, monotonically numbered extraction directory for every load.  This prevents an immediate `IOException`, but it does not prove the old context has collected. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/DllExtractor.cs:9-30, 87-101; prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:209-223)

13. **Collection happens after host-owned references release, not when `RemoveGroupAsync` returns.** The BundleHost comments identify a resident UI view-model retaining an old plugin instance until a deferred frame; the code queues old temp directories, retries `GC.Collect`/finalizers and recursive delete for about four seconds, and logs any still-pinned directory for a later reload or process exit.  Treating an API call named “unload” as a collection proof was the original error. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleHost.cs:20-24, 174-266)

14. **Exported-build GDScript logic did not hot-reload; only scene structure did.** The documented experiment found a rebuilt title-string behaviour did not change after reload, whereas re-instantiating a scene did.  Resident Godot-derived C# was deliberately non-reloadable as well, which is why resident surfaces were supposed to stay thin. (prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:57-80, 301-317)

15. **ALC type identity was a hard failure mode.** Contracts and any record carried by the bus/registry had to be loaded from the host parent via `SharedAssemblyPolicy`; otherwise `typeof(IFoo)`, MessagePipe's generic dispatch, and registry lookups became different types on opposite sides of the ALC and a plugin could load but do nothing.  This is the most transferable technical constraint, but it demands a deliberately short shared-contract allow-list—not a broad shared application assembly. (prior-attempt (2026-06-25) fantasim-app-godot/vault/architecture/load-unload-by-tier.md:96-119)

## 5. What Orc Bot should take

**Take, with a smaller scope.** RFC-0001 already has the right home for this: `contracts/OrcBot.Extensibility` remains an Orc-restricted adapter over PluginArchi, `plugins/` holds replaceable adapters, and `libs/` remains the policy owner.  Implement W5 with PluginArchi and RegistryArchi exactly as RFC-0001 proposes, but require every dynamically loaded group to declare a small shared-contract list, tag every RegistryArchi registration with its group owner, and pass an integration test that releases all host references then proves collection with PluginArchi diagnostics.  These are host mechanics and cleanup evidence, not an invitation to give an adapter application authority. (docs/rfc/0001-bootstrap-slice.md:43-61, 76-111; docs/surveys/S6-scarlet-reuse.md:20-54)

**Take the artifact discipline, not the PCK mechanism.** A named directory plus manifest and versioned output made historical Fantasim builds inspectable, and ADR-0005 already gives Orc Bot the stronger, repository-wide equivalent at `build/_artifacts/<version>/bundles/`.  If Orc Bot later needs an immutable payload format—for example a candidate evidence bundle—it should resemble the newest Fantasim world package: manifest plus digest-addressed bytes, read without loading executable code.  Candidate publication still remains an Orc Bot authority operation under ADR-0002. (prior-attempt (2026-06-25) fantasim-app-godot/Taskfile.yml:20-35; prior-attempt (2026-08-03) fantasim-app-godot/project/runtime/README.md:131-170; docs/adr/0002-fenced-source-allocations-and-immutable-candidates.md:18-45; docs/adr/0005-build-versioning-and-artifact-layout.md:30-46)

**Do not take the four-tier architecture.** Its strongest component—the T2 per-call proxy—is a solution to live replacement of running game services.  Orc Bot's v0 needs a durable daemon and explicit application surface, neither of which benefits from an extra ServiceArchi lifecycle; S6 and RFC-0001 already reject ServiceArchi and DependencyArchi for exactly that duplication.  Retain ordinary Contracts → Application/Core → plugin direction, with RegistryArchi selection only where W5 has multiple providers. (docs/rfc/0001-bootstrap-slice.md:99-110; docs/surveys/S6-scarlet-reuse.md:52-75)

**Do not add PCK hot reload to W12.** `complete-app` is validation configuration and a client of `orc`, not the product surface that needs downloadable UI panels.  Godot's non-unmountable PCK VFS, permanent resident Node layer, and unreliable exported GDScript reload would introduce a process-lifetime resource leak into the one place RFC-0001 needs repeatable observation.  Keep Godot content materialised in each allocation as ordinary source; seed its `.godot` cache per ADR-0009, and relaunch it for a changed host. (prior-attempt (2026-06-25) fantasim-app-godot/project/plugins/App.Bundles.Core/BundleVfs.cs:12-18; docs/rfc/0001-bootstrap-slice.md:251-269; docs/adr/0009-seed-engine-caches-do-not-share-them.md:27-52)

**Concrete RFC-0001 change:** none to the four-directory layout or W12 scope.  Clarify W5's acceptance criteria to require (1) owner-scoped registry cleanup, (2) explicit parent/shared-contract policy, and (3) a retained-reference negative unload test alongside a successful collectible unload test; clarify W12 that it deliberately reloads a fresh Godot process rather than PCKs.  Do not add ServiceArchi, DependencyArchi, CrosscutFoundation Messaging/Hosting, or GameFoundation to the bootstrap dependency graph.
